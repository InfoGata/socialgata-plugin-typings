## What this repo is

`@infogata/socialgata-plugin-typings` — the TypeScript type contract between [SocialGata](https://github.com/InfoGata/socialgata) (a plugin-based social media browser) and its plugins. There is no source code and no build: the package ships `index.d.ts` plus an empty `index.js`. Everything lives in one ambient `declare global { ... }` block, so plugin authors get the types by adding the package to `types` in their tsconfig or by `import`ing it — no named imports.

## Commands

```sh
npm test          # runs `tsc` (noEmit, strict) — the only check; validates index.d.ts

cd docs
npm start         # Docusaurus dev server (regenerates TypeDoc API pages from ../index.d.ts)
npm run build     # production build
npm run deploy    # deploy to GitHub Pages (infogata.github.io/socialgata-plugin-typings)
```

Releasing (CI publishes on tag push via npm OIDC trusted publishing — no NPM_TOKEN):

```sh
npm version <patch|minor|major>
git push --follow-tags
```

`.github/workflows/publish.yml` verifies the tag matches `package.json`, runs `npm test`, publishes, then cuts a GitHub Release.

## Architecture

**The `Application` interface is the whole API surface.** It has two kinds of members:

- **Host-provided methods** (non-optional: `networkRequest`, `getTheme`, `createNotification`, `postUiMessage`, `getCorsProxy`, `isLoggedIn`, `isNetworkRequestCorsDisabled`) — implemented by SocialGata, called by the plugin via the global `application` const. Plugins run in a sandboxed frame, so `networkRequest` (a `typeof fetch`) exists to proxy requests through the parent frame.
- **`on*` callbacks** (all optional) — implemented by the *plugin*, called by the host. Optionality is the capability model: a plugin advertises what it supports by which callbacks it defines. Adding a new plugin capability means adding an optional `on*` method here.

**Request/Response pairing.** Every `on*` data callback takes a `XRequest` and returns a `Promise<XResponse>`. Keep this symmetry when adding methods.

**Cross-cutting field conventions** — when adding a field, check whether it belongs to one of these families rather than inventing a new shape:

- `apiId` — the third-party service's id for an entity. `pluginId` and `instanceId` are set by the host / used for federation.
- `PageInfo` — the single pagination type; threaded through nearly every request and response.
- `sortId` / `timeRangeId` — a response advertises `SortOption[]` (each optionally carrying `TimeRange[]`), and the host echoes the chosen ids back on the next request. Present on the feed, community, user, community-search, and comments triads; these must stay in sync with each other.
- `FeedType` is orthogonal to `SortOption` — feed-type tabs and a sort selector can both be offered.
- `Post` is deliberately overloaded: it represents posts, comments (`parentId`, `comments`, `isSubmitter`), and imageboard replies (`number`). Comment-only and post-only fields coexist on it by design.

## Conventions

- Every declaration carries a JSDoc comment — TypeDoc renders these into the docs site, so a field without a doc comment ships as an undocumented API.
- Field additions are almost always optional (`?`) — a required field is a breaking change for every existing plugin.
- Keep `README.md`'s "Plugin Methods" list in sync when adding or removing an `on*` callback.
- `docs/docs/plugins/api/` is generated by `docusaurus-plugin-typedoc` on build and is gitignored — never hand-edit it.
